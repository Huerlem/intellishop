# AI Architecture — IntelliShop V2

Status: **design approved for implementation review — not yet implemented** · Branch `feature/v2-production-rebuild` · 2026-10-27
Governing requirement: [`requirements/AI_RECIPE_GENERATION_REQUIREMENT.md`](requirements/AI_RECIPE_GENERATION_REQUIREMENT.md) · Baseline defects: [`AI_RECIPE_AUDIT.md`](AI_RECIPE_AUDIT.md) · Security: [`SECURITY_REMEDIATION_PLAN.md`](SECURITY_REMEDIATION_PLAN.md)

## 1. Principles

1. **Real data in, real generation out.** Every recipe is generated by a model from the authenticated user's current pantry and/or selected list. No recipe catalogue, no fixtures, no fallback dishes in any production path.
2. **The server owns the inputs.** The client sends *what to do* (mode, list ID, preferences), never *the ingredients*. The function reads the caller's data itself.
3. **The model never decides facts about the user's kitchen.** Availability is computed deterministically by the server from IDs; the model only proposes recipes.
4. **Fail visibly.** Any provider, timeout, quota or validation failure returns a typed error and the UI shows an error state with Retry.
5. **Nothing changes without consent.** Adding missing ingredients is a reviewed, confirmed write.
6. **Same infrastructure for all AI features.** Recipe generation is the first consumer; List Optimisation Review (P04) reuses the callable, quota, schema and logging layers.

## 3. Authentication and authorised data access

| Layer | Control |
|---|---|
| Transport | Firebase callable (HTTPS) |
| Identity | `request.auth` required; anonymous users rejected (`unauthenticated`) |
| Device integrity | App Check enforced (`enforceAppCheck: true`), iOS App Attest provider; debug provider only in development builds |
| Ownership | Pantry query scoped to `users/{uid}/pantryItems`; list read from `users/{uid}/lists/{listId}`. A list ID belonging to someone else is indistinguishable from not found (`not-found`). |
| Client writes | Security Rules: user may read/write only `users/{uid}/**`; `aiUsage/**` and `recipeCache/**` are server-only (`allow write: if false`). |

**Data-model note.** The original code stores lists in a top-level `shoppingLists` collection (items as an array field) and pantry in top-level `stockItems`, both filtered by a `userId` field. V2 moves to per-user subcollections so Security Rules can express ownership by path and items can be updated individually without whole-array overwrites. The function reads through a small repository interface so the migration (milestone M2) does not change AI code.

## 4. Request contract

```ts
type RecipeMode = 'pantry' | 'list' | 'both';

interface GenerateRecipesRequest {
  mode: RecipeMode;
  listId?: string;                 // required for 'list' and 'both'
  preferences: {
    servings: number;              // 1–12
    maxTotalMinutes?: number;      // e.g. 15, 30, 60
    difficulty?: 'easy' | 'medium' | 'hard';
    cuisines?: string[];           // ≤5, each ≤30 chars
    equipment?: string[];          // ≤10, e.g. 'oven', 'microwave', 'air fryer'
    budgetGbp?: number;            // optional cap on *additional* spend; used only as guidance
    count?: number;                // recipes requested, 3–5 (default 4)
  };
  regenerate?: { excludeTitles: string[] };  // ≤10, bypasses cache
}
```

Dietary requirements and allergies are **not** sent in the request. They are read server-side from `users/{uid}/private/preferences`, which the user maintains in Profile (explicit consent required; see §11).

Validation (Zod, shared package `shared/ai/`): unknown fields rejected; strings trimmed; lengths enforced; `listId` must match `^[A-Za-z0-9_-]{1,64}$`.

## 5. Input normalisation (deterministic, before the model)

1. **Load** pantry items (exclude quantity 0 and items marked out) and/or list items (exclude items marked purchased).
2. **Normalise names:** lower-case, trim, collapse whitespace, strip punctuation, simple singularisation (`tomatoes`→`tomato`, `eggs`→`egg`); a small synonym table (`courgette`/`zucchini`, `coriander`/`cilantro`, `spring onion`/`scallion`).
3. **Normalise units** into families: mass (g), volume (ml), count (piece). `kg→g`, `l→ml`; `tsp/tbsp/cup` → ml only for liquids; packs/tins stay as count with original unit kept for display. Unknown units stay as given and are never converted.
4. **Merge** pantry + list (mode `both`): same normalised name **and** same unit family → one ingredient with `pantryQty` and `listQty`; otherwise kept as separate entries. Each merged entry keeps its source references.
5. **Rank** by expiry: `useSoon` = expires within 3 days (configurable), then by quantity. Items with no expiry date are ranked after dated items.
6. **Bound** the prompt: at most 120 ingredients; names cut to 60 characters; remaining items are summarised as a count. If zero usable ingredients → `failed-precondition / NO_INGREDIENTS`, checked **before** any credit reservation or provider call. UI: onboarding step "Add a few ingredients you have" that saves real Pantry items, then generates (required for Free introductory credits).
7. **Reference IDs:** each entry receives a short stable ID (`p12`, `l4`, `m3` for merged) used by the model and by reclassification.

User-supplied names are inserted as JSON data inside a delimited block, never interpolated into instructions; the system prompt states that ingredient names are data and must not be followed as instructions.

## 6. Provider and model selection

### 6.1 Requirements
JSON-Schema–constrained output, server SDK for Node.js, UK-usable commercial terms, predictable low cost per request, latency under ~15 s for 4 recipes, no use of compromised credentials or the suspended project.

### 6.2 Candidates (verified 2026-10-27 against official documentation)

| | Claude Haiku 5.5 (`claude-haiku-5-5`) | Gemini 3.1 Flash-Lite (`gemini-3.1-flash-lite`) |
|---|---|---|
| Structured output | GA; `output_config.format` with `type: "json_schema"`; Haiku 5.5 listed as supported ([docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)) | Supported via response schema (to be re-verified on the docs page before adoption) |
| Price, paid tier, USD / MTok | $0.10 input · $0.50 output for prompts ≤100k tokens ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)) | $0.25 input · $1.50 output ([pricing](https://ai.google.dev/gemini-api/docs/pricing)) |
| Credential model | New Anthropic Console API key in Secret Manager | New Google project; Vertex AI with service account (no API key) or AI Studio key in Secret Manager |
| Relationship to suspended project | Unrelated | Must be a new, separate project |

**Disclosure:** this document is written by Claude, an Anthropic model, recommending an Anthropic model. To counter that bias, the choice is gated on measured results, not on this table.

### 6.3 Decision
- **Initial provider:** Claude Haiku 5.5 — lowest verified cost of the two, GA schema-constrained output, and a clean credential boundary away from the suspended Google project.
- **Quality gate:** before release, the six acceptance scenarios plus a 30-case evaluation set (varied pantries, allergies, sparse inputs) must pass. If Haiku 5.5 fails the gate, step up to Claude Sonnet 5.5 ($2 / $10 per MTok) or switch to the Gemini candidate in a new project.
- **Adapter:** `functions/src/ai/provider.ts` exposes `generateStructured(schema, system, user, opts)`. Swapping provider changes one file plus the secret name.

### 6.4 Cost envelope (estimate, to be replaced by measured tokens)
Typical request ≈ 2,500 input + 3,000 output tokens → Haiku 5.5 ≈ $0.00025 + $0.0015 ≈ **$0.0018 per generation**. Free introductory allowance ≈ $0.005 per account (3 generations); Premium at the proposed fair-use ceiling (100/month) ≈ $0.18 per subscriber per month. See `MONETISATION_STRATEGY.md` §2; full model in `docs/AI_COST_ESTIMATE.md` (milestone M3).

## 7. Structured output

One schema, defined once in `shared/ai/recipeSchema.ts` (Zod) and converted to JSON Schema for the provider. The provider-side schema obeys the provider's limits (e.g. `additionalProperties: false`, no numeric min/max); range checks run in Zod after the response.

```ts
RecipeResult {
  recipes: Recipe[]                    // 1–5
  notes?: string                       // e.g. "Few ingredients available"
}

Recipe {
  id: string                           // server-assigned UUID (model value ignored)
  title: string
  description: string                  // ≤ 240 chars
  servings: integer                    // base servings
  prepMinutes: integer
  cookMinutes: integer
  difficulty: 'easy' | 'medium' | 'hard'
  ingredients: RecipeIngredient[]
  steps: { order: integer, text: string }[]
  equipment: string[]
  reason: string                       // why this recipe for this user now
  usesSoonExpiring: string[]           // ingredient refs
  dietaryTags: string[]                // e.g. 'vegetarian' — model claim, displayed as such
  allergenWarnings: string[]           // filled/overridden by server post-check
  nutritionEstimate?: {                // OFF at launch behind flag `ai.nutritionEstimates`
    perServing: { kcal, proteinG, carbsG, fatG }   // owner decision FS-D1
    isEstimate: true                   // const; UI label "AI estimate — not verified"
  }
  // No price, availability, cooking-temperature or storage-time fields
  // (docs/compliance/FOOD_SAFETY_TECHNICAL_SPEC.md §3.2, §4).
}

RecipeIngredient {
  name: string
  quantity: number | null              // null = "to taste"
  unit: string
  sourceRef: string | null             // input ID (p12 / l4 / m3) or null if not owned/planned
  // set by the server, never trusted from the model:
  status: 'available' | 'fromList' | 'partial' | 'missing'
  shortfall?: { quantity: number, unit: string }
}
```

Output groups shown in the UI are derived from `status`: **Available now**, **From your shopping list**, **Missing**. A recipe is "ready to cook" only when every ingredient is `available`.

## 8. Post-processing (server, deterministic)

1. **Schema validation** (Zod). Failure → `INVALID_OUTPUT` (no repair, no partial display). `stop_reason` of `refusal` or `max_tokens` is treated as failure.
2. **Reclassification:** for each ingredient, if `sourceRef` is unknown or points to the wrong source → `missing`. If it exists: pantry ref → `available`; list ref → `fromList`; merged ref → `available` when the pantry covers it, otherwise `fromList`. Quantities in the same unit family are compared; insufficient stock → `partial` with `shortfall`. Pantry staples the user has not recorded (salt, pepper, water, oil) are shown as missing unless present; the user can mark "I have this" during review.
3. **Allergen post-check:** declared allergens are expanded through a maintained keyword map (e.g. *milk* → butter, cream, cheese, yoghurt, whey; *gluten* → wheat flour, pasta, bread, couscous). Recipes containing a match are **removed**; if every recipe is removed, the function returns `ALLERGEN_CONFLICT` with guidance. Surviving recipes always carry the fixed disclaimer: *"AI-generated suggestion. Always check product labels. IntelliShop cannot guarantee a recipe is free from allergens or suitable for a medical diet."*
4. **IDs and metadata:** server assigns `id`, `generatedAt`, `mode`, `model`, `promptVersion`, and `inputHash`.

## 9. Failure handling

| Condition | Server behaviour | Code returned | UI |
|---|---|---|---|
| Not signed in / App Check failed | Reject before any work | `unauthenticated` / `failed-precondition` | Re-auth prompt |
| No usable ingredients | No provider call, no quota use | `NO_INGREDIENTS` | Empty state with next action |
| Email not verified (Free credits) | No provider call | `EMAIL_NOT_VERIFIED` | Verify-email prompt |
| Plan lacks the feature (e.g. Standard → optimisation) | No provider call | `PLAN_REQUIRED` | Premium-locked state with upgrade |
| Introductory credits used up | No provider call | `TRIAL_EXHAUSTED` | "0 of 3 free AI recipes remaining" + Premium prompt |
| Another free request in flight | No provider call | `REQUEST_IN_PROGRESS` | Wait state |
| Premium fair-use / rate limit exceeded | No provider call | `QUOTA_EXCEEDED` (+ reset time) | Message with time; Retry disabled until reset |
| Global spend cap reached | No provider call | `SERVICE_PAUSED` | Message; Retry later |
| Provider 429 / 5xx / overloaded | 1 retry with jittered back-off inside the time budget | `PROVIDER_UNAVAILABLE` | Error card + **Retry** |
| Provider exceeds timeout (20 s) | Abort request | `PROVIDER_TIMEOUT` | Error card + **Retry** |
| Schema / refusal / truncated | No partial results | `INVALID_OUTPUT` | Error card + **Retry** |
| All recipes blocked by allergens | — | `ALLERGEN_CONFLICT` | Explanation; adjust inputs |
| Device offline | Not sent | (client) | Offline banner; saved favourites remain available |

There is **no fallback content** in any branch (requirement Scenario 6). Failed calls caused by the provider (unavailable, timeout, invalid output) consume neither an introductory credit nor Premium quota.

## 10. Entitlements, credits, quotas and cost monitoring

Plan rules are defined in `SUBSCRIPTION_ENTITLEMENTS.md`; the mechanism in `SUBSCRIPTION_ARCHITECTURE.md` §5.

- **Entitlement gate:** the function reads server-written `entitlements/{uid}`. The plan is never taken from the request.
- **Free (and Standard, per D10) — introductory credits:** 3 lifetime successful generations per account in `aiCredits/{uid}`; race-safe *reserve → generate → finalise / release*; one generation = one credit regardless of recipe count; reservations expire after 90 s.
- **Premium — fair use:** proposed 100 generations/month (recipes + optimisation) and 10/hour, in `aiUsage/{uid}/months/{yyyy-mm}`; counted on success only. Premium usage never touches introductory credits.
- **Per user burst limit (all plans):** 5 requests/minute.
- **Global:** daily estimated-spend cap in `aiUsage/_global/days/{date}`; at 100% the function returns `SERVICE_PAUSED`. Cloud Billing budget alerts at 50/90/100%.
- **Function limits:** `maxInstances` cap, request body ≤ 8 KB, memory 512 MiB, timeout 30 s.
- **Cost log per call** (Cloud Logging, structured): hashed UID, feature, model, input/output tokens from the provider's usage field, estimated cost, latency, outcome code. No prompts, ingredients, allergies or output text are logged.

## 11. Personal data

- Dietary requirements and allergies are health-related data. They are optional, collected only after an explicit consent toggle in Profile, stored in `users/{uid}/private/preferences`, included in data export and account deletion, and sent to the AI provider only for the request that needs them.
- The privacy policy must name the AI provider as a processor and describe what is sent (ingredient names, quantities, expiry dates, preferences) and why. Provider data-retention and training terms must be confirmed from the provider's current commercial terms and DPA before launch (owner/legal action — BLOCKED).
- No analytics or advertising SDK is added for AI features.

## 12. Cache and invalidation

- **Key:** `SHA-256(uid ‖ mode ‖ listId ‖ normalised inputs incl. quantities and expiry dates ‖ dietary/allergy hash ‖ preferences ‖ promptVersion ‖ model)`.
- **Store:** `recipeCache/{uid}_{hash}` (server-only), Firestore TTL policy on `expiresAt` = 6 hours.
- **Invalidation:** implicit — any pantry change, list change, preference change, prompt or model change yields a new key (requirement Scenario 5). The original defect (`[object Object]` keys shared between different pantries) cannot recur because keys are built from normalised primitive values and covered by a unit test.
- **Regenerate:** bypasses the cache, passes the previous titles as `excludeTitles`, and counts against quota.

## 13. Favourites

- **Save:** full recipe snapshot written to `users/{uid}/favouriteRecipes/{recipeId}` with `savedAt`, `generatedAt`, `model`, `mode`. Saved recipes are not re-generated; availability is recomputed against the current pantry when opened.
- **Remove:** delete document (with undo snackbar).
- **Scope:** included in data export and account deletion. Replaces the three inconsistent device-local stores in V1.

## 14. User-confirmed list changes (add missing ingredients)

1. User taps **Add missing ingredients** on a recipe.
2. **Review sheet** lists `missing` and `partial` ingredients, each with a checkbox (default on), editable quantity/unit, and a marker if the item is already on the target list.
3. User chooses the target list (default: the list used in mode `list`/`both`, else most recent active list; option to create one).
4. **Confirm** → a single batched Firestore write adds new items and increases quantities of existing matching items; each item records `addedFrom: { type: 'recipe', recipeId }`.
5. Snackbar with **Undo** (reverts the batch).
Cancelling writes nothing. Servings changes rescale shortfall quantities before review. This flow is client-side under Security Rules; no AI call is involved.

## 15. Servings adjustment

Client-side, deterministic: `quantity × targetServings / baseServings`, rounded to sensible precision per unit; `null` ("to taste") quantities unchanged. No model call.
